# Build

Work in a worktree from main on branch `<story|bug|refactor|chore>/<key>-<title-words>`, the key being the ticket's, else a short slug. A change with one obvious result and no trade-off, such as a colour or a config value, needs none of this: make it and let the check run.

The check is the `Check:` command in `AGENTS.md`. The real-data run is the way to see it work agreed in step 1; it writes nothing live.

1. **Align** with the person on what you are building, why it is needed, and what it enables once done. First tell them what in the code or a decision record affects it, each with its `file:line`. Offer any easier way, and reuse what the repository already has rather than build it again. You are aligned when you both agree on criteria a test can decide deterministically, each a rule with a Given/When/Then example in real values, failure paths included, and on the real-data run, against real data or the running app. Every number, bar or rule a criterion needs is the person's. Ask in chat, scaled to the change: a request stated in full, naming the result and every value it needs, gets `Done when:` lines, each one result a test or run shows, with no example; a rule with many cases gets a table of examples. A story or ticket that already answers these is the answer; ask only what it lacks.
   * **A bug:** behaviour nobody built is a feature; say so in one line and align on it as one. Otherwise reproduce it before anything else: the reproduction is the first criterion, and running it again is the real-data run. Asked only why it happens, answer with the reproduction and offer the fix. Cannot reproduce: ask for the missing fact by name and stop. When it loses or exposes data, or blocks every user, first tell the person the step that stops the harm, such as a revert or a flag off.
   * **A refactor:** the criterion is that every existing test passes unchanged. Commit characterization tests and refactor by [references/refactor.md](references/refactor.md), then go to step 7.
   * **A chore,** such as a dependency bump: its `Done when:` lines are the check and the real-data run passing after it. Make the change, then go to step 7.
2. **Review the criteria** against [references/criteria.md](references/criteria.md), as `AC<n>: <failure mode> — "<quoted text>" — <fix>`. When you drafted a criterion, a fresh subagent reviews them instead, given the criteria, the worktree and that file's path. Fix slips of wording yourself and show the person the rest; they revise or keep each, and a kept one goes under `Open questions` with its risk. When the person asks for a story, write it up in that file's form. A request only for a story or a critique ends here.
3. **Plan** how it will be built, by [references/design-spec.md](references/design-spec.md), skipped for a change with one obvious approach; a plan the person brings is the plan. Have a fresh subagent review it, given only the plan, the criteria and the worktree, and fix each blocking finding.
4. **Hard-to-reverse decisions** from the criteria and the plan go to the person, the options as equals: data stored or sent, a contract others call, a new dependency, auth, how it deploys, or how the parts are split.
5. **Failing tests first,** by [references/tests.md](references/tests.md). See each fail for the right reason, commit them alone, the message starting `test(red):`, and show the person each of its `Questions:`. A criterion changed after that commit goes through step 2 again, and its tests go in a new `test(red):` commit before any code.
6. **Implement** by a fresh subagent, one launch at a time, given the worktree, the red commits, the criteria, the `Decided:` lines, the check and the paths of the tests and refactor references. Trust `git log` and the check over its return. Settle each `blocked:` line by the criterion's words, asking the person when both readings fit; a test changes only when its criterion shows it wrong, in a new `test(red):` commit, then relaunch. Where `AGENTS.md` has a `Mutation:` line, run it on the changed files and add a test that kills each surviving mutant in a changed line, in a `test:` commit, since it passes from the start.
7. **Review** by fresh subagents. Put `diff.patch`, the diff against the merge target, and `story.md`, the criteria and each test changed after it was first committed, with why, in `<temp>/review-<timestamp>/`. One reviews it, given that directory, the worktree and the merge target; another verifies its findings, given only its `findings.md`, the worktree, `diff.patch`, `story.md` and the check. Tell the person each kept finding in one line. Fix each blocking one test-first: its failing test by step 5, its code by step 6. Then do the real-data run.
8. **Pull request** into main, titled `[<key>] <what it does, imperative>`, body by [references/pull-request.md](references/pull-request.md); past about 400 changed lines, split it by criterion. Watch CI and review comments until it merges, fixing each failure and each comment you agree with, test-first where a test can show it, and replying to each comment. After merge, remove the worktree and the branch.

Record each choice you make alone as `Decided: <choice>, because <reason>`. One you would recommend, that is easy to reverse and that no criterion states, such as how rows are ordered, goes in the pull request, never a stop. Wait for the person's answer at steps 1, 2 and 4, and elsewhere only for a hard-to-reverse decision, a number or rule a criterion needs, a criterion the code contradicts, or a fact only the person has; otherwise go on with your pick and tell them. With no person in the session, ask on the ticket's issue or the pull request, else in your final report, go on with the work that does not wait on the answer, then stop and say what waits.
